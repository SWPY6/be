# 명세 주도 개발 (Spec-Driven Development)

## 개요

코드를 한 줄이라도 쓰기 전에 구조화된 명세(spec)를 작성한다. 명세는 나와 사람 엔지니어가 공유하는 단일 진실 공급원이다 — 무엇을 만드는지, 왜 만드는지, 무엇을 만족하면 끝난 것인지를 정의한다. 명세 없는 코드는 추측이다.

## 언제 사용하는가

- 새 프로젝트나 기능을 시작할 때
- 요구사항이 모호하거나 불완전할 때
- 변경이 여러 파일이나 모듈에 걸칠 때
- 아키텍처 결정을 내리기 직전일 때
- 구현에 30분 이상 걸리는 작업일 때

**사용하지 않을 때:** 한 줄짜리 수정, 오타 교정, 또는 요구사항이 명확하고 그 자체로 완결된 변경.

## 게이트 워크플로

명세 주도 개발은 네 단계로 이루어지며, 그 앞에 범위 점검(Phase 0)이 붙는다. 범위 점검은 하나의 요청이 독립적으로 테스트 가능한 여러 기능을 묶고 있을 때만 발동한다. 현재 단계가 검증되기 전에는 다음 단계로 넘어가지 않는다.

```
SPECIFY ──→ PLAN ──→ TASKS ──→ IMPLEMENT
   │          │        │          │
   ▼          ▼        ▼          ▼
  사람        사람      사람       사람
  검토        검토      검토       검토
```

### Phase 0: 범위 점검

대부분의 요청은 하나의 기능을 설명한다. 이번 요청도 그렇다면 이 단계를 건너뛰고 바로 Specify로 간다 — Phase 0은 예외를 위한 것이지 규칙이 아니며, 단일 기능짜리 feature에 계층 구조를 씌우지 않는다.

**판별.** 하나의 요구사항이 독립적으로 테스트 가능한 여러 기능을 묶고 있다면 명세를 쓰기 전에 분해한다:

- 요구사항이 각자의 사용자나 데이터를 가진 별개의 기능들을 나열한다 (예: 인증, 결제, 알림, 리포팅)
- 인수 기준이 따로 출시하고 따로 검증할 수 있는 그룹으로 뭉친다
- 어느 한 기능을 잘라내거나 교체해도 나머지 기능의 요구사항을 다시 쓸 필요가 없다

**명세를 쓰기 전에 기능 맵(capability map)을 먼저 제안한다.** 작고 검토 가능해야 한다 — 프로젝트 계획서가 아니라 모듈 표 하나와 빌드 순서다:

```markdown
# 기능 맵: [이니셔티브 이름]

| 모듈 id | 책임 | 의존 대상 |
|---|---|---|
| identity | 계정, 세션, SSO | — |
| billing | 요금제, 청구서, 결제 | identity |
| notifications | 이메일·웹훅 팬아웃 | identity |
| reporting | 사용량 대시보드 | billing, notifications |

빌드 순서: identity → billing, notifications → reporting
```

- **모듈 id는 고정한다.** 케밥 케이스로 한 번 정하고, 이니셔티브 중간에 절대 이름을 바꾸지 않는다. 명세, 계획, 하위 커맨드는 어떤 명세가 활성 상태인지 추측하는 대신 이 id로 작업을 지정한다.
- **의존 방향은 한쪽으로, 순환은 금지.** 화살표는 한 방향만 가리킨다. 두 모듈이 서로를 필요로 한다면 그것은 하나의 모듈이다.
- **인터페이스는 경계에 둔다.** 맵은 `billing`이 `identity`에 의존한다는 사실만 기록한다. 둘 사이의 계약은 제공하는 쪽 모듈의 명세에 들어간다 (설계 방법은 `api-and-interface-design` 참고).

**맵도 다른 단계와 똑같이 게이트를 거친다.** 모듈 명세를 하나라도 쓰기 전에, 사람이 모듈 경계·의존 방향·빌드 순서를 검토한다. 맵을 잘못 잡으면 비용이 크지만, 열 줄을 검토하는 비용은 크지 않다.

**그다음 모듈별로 재귀한다.** 의존 순서대로 각 모듈에 대해 Specify → Plan → Tasks → Implement를 돌린다. 각 모듈은 그 모듈의 목표·경계·성공 기준으로 범위가 좁혀진 자기 명세를 갖는다. 승인된 맵은 `docs/CAPABILITY-MAP.md`에 저장하고, 각 모듈의 명세는 그 옆에 모듈 id로 이름 붙여 둔다 (`docs/SPEC-identity.md`, `docs/SPEC-billing.md`) — 무엇이 존재하는지에 대한 색인은 파일명 추측이 아니라 맵이다.

### Phase 1: Specify (명세)

큰 그림에서 시작한다. 요구사항이 구체적이 될 때까지 사람에게 명확화 질문을 던진다.

**전제를 즉시 드러낸다.** 명세 내용을 쓰기 전에 내가 무엇을 가정하고 있는지부터 나열한다:

```
내가 세운 전제:
1. 이것은 JSON을 반환하는 REST API다 (서버 렌더링 화면이 아니다)
2. 인증은 세션 기반이다 (기존 SecurityConfig 기준, JWT가 아니다)
3. 데이터베이스는 MySQL이다 (build.gradle의 mysql-connector-j 기준)
4. 트랜잭션 경계는 서비스 계층에 둔다
→ 지금 바로잡아 주지 않으면 이대로 진행한다.
```

모호한 요구사항을 말없이 채워 넣지 않는다. 명세의 존재 이유 자체가 코드가 쓰이기 *전에* 오해를 드러내는 것이고, 전제는 가장 위험한 형태의 오해다.

**명세 문서는 다음 여섯 가지 핵심 영역을 다룬다:**

1. **목표(Objective)** — 무엇을 왜 만드는가? 사용자는 누구인가? 성공은 어떤 모습인가?

2. **명령어(Commands)** — 도구 이름만이 아니라 플래그까지 포함한 실행 가능한 전체 명령.
   ```
   Build: ./gradlew build
   Test: ./gradlew test
   Single test: ./gradlew test --tests '*TaskServiceTest'
   Compile: ./gradlew compileJava
   Run: ./gradlew bootRun
   ```

3. **프로젝트 구조(Project Structure)** — 소스가 어디에 있고, 테스트가 어디로 가고, 문서가 어디에 속하는지.
   ```
   src/main/java/org/example/ploutos/   → 애플리케이션 소스 코드
   src/main/java/.../<도메인>/           → 도메인별 엔티티·서비스·컨트롤러
   src/main/java/.../common/            → 공용 예외 처리, 응답 포맷
   src/main/resources/                  → application.yml, 마이그레이션
   src/test/java/                       → 테스트 (소스와 같은 패키지 구조)
   ```

4. **코드 스타일(Code Style)** — 스타일을 설명하는 세 문단보다 실제 코드 스니펫 하나가 낫다. 네이밍 규칙, 포매팅 규칙, 좋은 출력의 예시를 포함한다.

5. **테스트 전략(Testing Strategy)** — 어떤 프레임워크를 쓰고, 테스트가 어디에 있고, 커버리지 기대치는 무엇이며, 어떤 관심사를 어떤 테스트 레벨로 다루는지.

6. **경계(Boundaries)** — 3단 체계:
   - **항상 한다:** 커밋 전 테스트 실행, 네이밍 규칙 준수, 입력 검증
   - **먼저 묻는다:** 데이터베이스 스키마 변경, 의존성 추가, CI 설정 변경
   - **절대 안 한다:** 비밀값 커밋, vendor 디렉토리 수정, 승인 없이 실패하는 테스트 삭제

**명세 템플릿:**

```markdown
# 명세: [프로젝트/기능 이름]

## 목표
[무엇을 왜 만드는가. 사용자 스토리 또는 인수 기준.]

## 기술 스택
[프레임워크, 언어, 주요 의존성과 버전]

## 명령어
[빌드, 테스트, 린트, 개발 서버 — 전체 명령]

## 프로젝트 구조
[디렉토리 레이아웃과 설명]

## 코드 스타일
[예시 스니펫 + 핵심 규칙]

## 테스트 전략
[프레임워크, 테스트 위치, 커버리지 요구치, 테스트 레벨]

## 경계
- 항상: [...]
- 먼저 묻기: [...]
- 절대 안 함: [...]

## 성공 기준
[무엇을 만족하면 끝인가 — 구체적이고 테스트 가능한 조건]

## 미해결 질문
[사람의 입력이 필요한 미결 사항]
```

**완성한 명세는 `docs/SPEC-<모듈id>.md`로 저장한다.** 모듈 id는 케밥 케이스로 한 번 정하고 중간에 바꾸지 않는다. 기능이 하나뿐이라면 기능 맵 없이 명세 파일 하나만 만든다.

**지시를 성공 기준으로 바꿔 쓴다.** 모호한 요구사항을 받으면 구체적인 조건으로 번역한다:

```
요구사항: "할 일 목록 API를 더 빠르게 만들어 줘"

성공 기준으로 재구성:
- 항목 1만 건 기준 GET /api/tasks p95 응답 시간 < 200ms
- 목록 한 페이지 조회 시 발생하는 쿼리 수 3개 이하 (N+1 제거)
- 위 두 조건을 검증하는 테스트가 존재한다
→ 이 목표치가 맞습니까?
```

이렇게 하면 "더 빠르게"가 무슨 뜻인지 추측하는 대신, 명확한 목표를 향해 반복하고 재시도하며 문제를 풀어 나갈 수 있다.

### Phase 2: Plan (계획)

검증된 명세를 가지고 기술 구현 계획을 만든다:

1. 주요 컴포넌트와 그들 사이의 의존 관계를 식별한다
2. 구현 순서를 정한다 (무엇이 먼저 만들어져야 하는가)
3. 위험 요소와 완화 전략을 기록한다
4. 병렬로 만들 수 있는 것과 반드시 순차적이어야 하는 것을 구분한다
5. 단계 사이의 검증 체크포인트를 정의한다

> 위 단계들의 바탕이 되는 의존 그래프 매핑과 수직 슬라이싱 기법은 `planning-and-task-breakdown`을 따른다. 그쪽이 정본이다. 위의 항목들은 요약이며, 둘이 어긋나면 `planning-and-task-breakdown`이 우선한다.
>
> **출력 규약:** 계획은 `tasks/plan.md`에 저장하고, 태스크 목록은 `planning-and-task-breakdown`이 정의한 태스크 목록 위치에 기록한다 (기본값 `tasks/todo.md`. 프로젝트가 외부 트래커를 지정할 수도 있다). `tasks/`가 없으면 만든다. 하위 커맨드(`/build` 등)는 이 기본값을 전제한다.

계획은 검토 가능해야 한다. 사람이 읽고 "그래, 그 방향이 맞다" 또는 "아니, X를 바꿔라"라고 말할 수 있어야 한다.

### Phase 3: Tasks (태스크)

계획을 개별적으로 구현 가능한 태스크로 쪼갠다:

- 각 태스크는 한 번의 집중된 세션에 끝낼 수 있어야 한다
- 각 태스크는 명시적인 인수 기준을 갖는다
- 각 태스크는 검증 단계(테스트, 빌드, 수동 확인)를 포함한다
- 태스크는 중요도가 아니라 의존 관계로 정렬한다
- 어떤 태스크도 파일 5개 이상을 건드리지 않는다

> 태스크 크기 산정과 의존 순서 결정의 전체 기법은 `planning-and-task-breakdown`을 따른다. 그쪽이 정본이다. 아래 템플릿은 간이 인라인 형식이며, 둘이 어긋나면 `planning-and-task-breakdown`이 우선한다.

**태스크 템플릿:**
```markdown
- [ ] 태스크: [설명]
  - 인수 기준: [끝났을 때 참이어야 하는 것]
  - 검증: [확인 방법 — 테스트 명령, 빌드, 수동 확인]
  - 파일: [건드릴 파일들]
```

### Phase 4: Implement (구현)

`.claude/skills/incremental-implementation/SKILL.md`(`incremental-implementation`)와 `.claude/skills/test-driven-development/SKILL.md`(`test-driven-development`)를 따라 태스크를 하나씩 실행한다. 명세 전체를 통째로 밀어 넣는 대신 각 단계에 맞는 명세 섹션과 소스 파일만 올리려면 `.claude/skills/context-engineering/SKILL.md`(`context-engineering`)를 사용한다.

## 명세를 살아 있게 유지하기

명세는 일회성 산출물이 아니라 살아 있는 문서다:

- **결정이 바뀌면 갱신한다** — 데이터 모델을 바꿔야 한다는 걸 발견하면, 명세를 먼저 고치고 그다음 구현한다.
- **범위가 바뀌면 갱신한다** — 추가되거나 잘려 나간 기능은 명세에 반영한다.
- **명세를 커밋한다** — 명세는 코드와 나란히 버전 관리에 들어간다.
- **PR에서 명세를 참조한다** — 각 PR이 구현하는 명세 섹션으로 역링크를 건다.

## 흔한 자기합리화

| 자기합리화 | 실제로는 |
|---|---|
| "이건 단순하니까 명세는 필요 없어" | 단순한 작업에 *긴* 명세는 필요 없지만, 인수 기준은 여전히 필요하다. 두 줄짜리 명세도 명세다. |
| "코드부터 짜고 명세는 나중에 쓸게" | 그건 명세가 아니라 문서화다. 명세의 가치는 코드 *이전에* 명확성을 강제하는 데 있다. |
| "명세는 속도를 늦춰" | 15분짜리 명세가 몇 시간의 재작업을 막는다. 15분짜리 폭포수가 15시간짜리 디버깅보다 낫다. |
| "어차피 요구사항은 바뀔 텐데" | 그래서 명세가 살아 있는 문서인 것이다. 낡은 명세도 명세 없는 것보다는 낫다. |
| "사용자는 자기가 뭘 원하는지 알아" | 명확해 보이는 요청에도 암묵적 전제가 있다. 명세는 그 전제를 드러낸다. |
| "하나의 큰 기능인데 쪼개는 건 오버헤드야" | 인수 기준이 독립적으로 테스트 가능한 그룹으로 뭉친다면, 통짜 명세는 이후 모든 태스크가 계약 전체를 놓고 판단하도록 강요한다. 열 줄짜리 기능 맵이 훨씬 싼 대안이다. |
| "계획 단계에서 분해하면 돼" | 계획은 하나의 명세 *안에서* 태스크를 나눈다. 그 시점에는 이미 과대한 산출물이 존재한다. 모듈 경계와 의존 방향은 명세를 쓴 뒤가 아니라 쓰기 전에 정해야 한다. |

## 위험 신호

- 문서화된 요구사항 없이 코드를 쓰기 시작한다
- "끝"이 무엇인지 명확히 하기 전에 "그냥 만들기 시작할까요?"라고 묻는다
- 어떤 명세나 태스크 목록에도 없는 기능을 구현한다
- 아키텍처 결정을 문서화 없이 내린다
- "뭘 만들지는 뻔하니까"라는 이유로 명세를 건너뛴다
- 하나의 명세가 독립적으로 테스트 가능한 여러 기능에 걸친 요구사항을 담고 있다
- 승인된 기능 맵이 없어서 모듈 경계나 빌드 순서가 구현 중에 암묵적으로 정해진다

## 검증

구현으로 넘어가기 전에 확인한다:

- [ ] 명세가 여섯 가지 핵심 영역을 모두 다룬다
- [ ] 사람이 명세를 검토하고 승인했다
- [ ] 성공 기준이 구체적이고 테스트 가능하다
- [ ] 경계(항상/먼저 묻기/절대 안 함)가 정의되어 있다
- [ ] 명세가 `docs/SPEC-<모듈id>.md`로 저장되어 있다
- [ ] 요청이 독립적으로 테스트 가능한 여러 기능을 묶는다면, 모듈 명세를 하나라도 쓰기 전에 기능 맵(모듈 id, 의존 방향, 빌드 순서)이 승인되었다
- [ ] 모든 모듈 명세가 승인된 맵의 모듈 id로 추적된다
