# 계획 수립과 태스크 분해 (Planning and Task Breakdown)

## 개요

작업을 명시적인 인수 기준을 갖춘 작고 검증 가능한 태스크로 분해한다. 좋은 태스크 분해는 작업을 안정적으로 끝내는 에이전트와 엉킨 실타래를 만들어 내는 에이전트를 가르는 차이다. 모든 태스크는 한 번의 집중된 세션 안에서 구현하고, 테스트하고, 검증할 수 있을 만큼 작아야 한다.

## 언제 사용하는가

- 명세가 있고 이를 구현 단위로 쪼개야 할 때
- 태스크가 너무 크거나 막연해서 시작하기 어려울 때
- 여러 에이전트나 세션에 작업을 병렬로 나눠야 할 때
- 사람에게 범위를 전달해야 할 때
- 구현 순서가 자명하지 않을 때

**사용하지 않을 때:** 범위가 명확한 단일 파일 변경, 또는 명세가 이미 잘 정의된 태스크를 담고 있을 때.

## 계획 수립 과정

### 1단계: 계획 모드로 들어간다

코드를 쓰기 전에 읽기 전용으로 동작한다:

- 명세와 관련 코드베이스 영역을 읽는다
- 기존 패턴과 규약을 파악한다
- 컴포넌트 사이의 의존 관계를 매핑한다
- 위험 요소와 미지수를 기록한다

**계획 중에는 코드를 쓰지 않는다.** 산출물은 `tasks/plan.md`에 저장된 계획 문서와 태스크 목록 위치에 기록된 태스크 목록(출력 파일 절 참고. 기본값 `tasks/todo.md`)이지 구현물이 아니다.

### 2단계: 의존 그래프를 파악한다

무엇이 무엇에 의존하는지 매핑한다:

```
데이터베이스 스키마
    │
    ├── 엔티티 / 값 객체
    │       │
    │       ├── 리포지토리
    │       │       │
    │       │       └── 서비스 (도메인 규칙, 트랜잭션)
    │       │               │
    │       │               └── 컨트롤러 (요청/응답 record)
    │       │
    │       └── 검증 규칙
    │
    └── 초기 데이터 / 마이그레이션
```

구현 순서는 의존 그래프를 아래에서 위로 따라간다: 기반부터 만든다.

### 3단계: 수직으로 슬라이스한다

데이터베이스를 전부 만들고, 그다음 API를 전부, 그다음 UI를 전부 만드는 대신 — 한 번에 하나의 완결된 기능 경로를 만든다:

**나쁨 (수평 슬라이싱):**
```
태스크 1: 데이터베이스 스키마 전체 구축
태스크 2: 모든 엔티티와 리포지토리 구축
태스크 3: 모든 컨트롤러 구축
태스크 4: 전부 연결
```

**좋음 (수직 슬라이싱):**
```
태스크 1: 계정을 만들 수 있다 (가입 스키마 + 서비스 + POST /api/users)
태스크 2: 로그인할 수 있다 (인증 설정 + 서비스 + POST /api/auth/login)
태스크 3: 할 일을 만들 수 있다 (할 일 스키마 + 서비스 + POST /api/tasks)
태스크 4: 할 일 목록을 볼 수 있다 (조회 + 페이징 + GET /api/tasks)
```

각 수직 슬라이스는 동작하고 테스트 가능한 기능을 전달한다.

### 4단계: 태스크를 작성한다

각 태스크는 마크다운 태스크 목록에 들어가든 외부 트래커의 항목으로 들어가든 다음 구조를 따른다 (출력 파일 절 참고):

```markdown
## 태스크 [N]: [짧은 설명형 제목]

**설명:** 이 태스크가 무엇을 달성하는지 한 문단으로.

**인수 기준:**
- [ ] [구체적이고 테스트 가능한 조건]
- [ ] [구체적이고 테스트 가능한 조건]

**검증:**
- [ ] 테스트 통과: `./gradlew test --tests '*TaskServiceTest'`
- [ ] 빌드 성공: `./gradlew build`
- [ ] 수동 확인: [무엇을 확인할지에 대한 설명]

**의존 대상:** [의존하는 태스크 번호, 없으면 "없음"]

**건드릴 가능성이 있는 파일:**
- `src/main/java/org/example/ploutos/task/TaskService.java`
- `src/test/java/org/example/ploutos/task/TaskServiceTest.java`

**예상 범위:** [Small: 1-2 파일 | Medium: 3-5 파일 | Large: 5+ 파일]
```

### 5단계: 순서를 정하고 체크포인트를 둔다

다음을 만족하도록 태스크를 배치한다:

1. 의존 관계가 충족된다 (기반을 먼저 만든다)
2. 각 태스크가 끝난 뒤 시스템이 동작하는 상태로 남는다
3. 태스크 2~3개마다 검증 체크포인트가 온다
4. 위험이 큰 태스크를 앞쪽에 둔다 (빨리 실패한다)

태스크 목록 위치에 명시적인 체크포인트를 추가한다:

```markdown
## 체크포인트: 태스크 1-3 이후
- [ ] 모든 테스트 통과
- [ ] `./gradlew build`가 에러 없이 통과함
- [ ] 핵심 사용자 플로가 종단 간으로 동작함
- [ ] 진행 전 사람과 함께 검토
```

## 태스크 크기 가이드

| 크기 | 파일 수 | 범위 | 예시 |
|------|-------|-------|---------|
| **XS** | 1 | 함수 하나 또는 설정 변경 | 검증 규칙 하나 추가 |
| **S** | 1-2 | 컴포넌트 하나 또는 엔드포인트 하나 | 새 API 엔드포인트 추가 |
| **M** | 3-5 | 기능 슬라이스 하나 | 사용자 가입 플로 |
| **L** | 5-8 | 여러 컴포넌트에 걸친 기능 | 필터링과 페이지네이션이 있는 검색 |
| **XL** | 8+ | **너무 큼 — 더 쪼갤 것** | — |

태스크가 L 이상이면 더 작은 태스크로 쪼개야 한다. 에이전트는 S와 M 크기 태스크에서 가장 잘 동작한다.

**태스크를 더 쪼개야 하는 신호:**
- 한 번의 집중된 세션으로 안 끝난다 (에이전트 작업 기준 대략 2시간 이상)
- 인수 기준을 세 개 이하의 항목으로 서술할 수 없다
- 서로 독립적인 두 개 이상의 서브시스템을 건드린다 (예: 인증과 결제)
- 태스크 제목에 "그리고"를 쓰고 있다 (두 개의 태스크라는 신호)

## 출력 파일

- **계획 문서:** 구현 계획은 `tasks/plan.md`에 저장한다. 이건 항상 마크다운 파일이다 — 설계 결정, 위험, 미해결 질문은 개별 트래커 이슈에 깔끔하게 대응되지 않는다.
- **태스크 목록:** 각 태스크를 **태스크 목록 위치**(아래 정의)에 기록한다.

`tasks/` 디렉토리가 없으면 만든다.

**미완성 계획을 절대 덮어쓰지 않는다.** `tasks/plan.md`나 `tasks/todo.md`를 쓰기 전에, 이미 존재하며 체크되지 않은 태스크가 남아 있는지 확인한다:

- 같은 작업을 다시 계획하는 경우 (사용자가 이 계획의 수정이나 확장을 요청) → 기존 파일을 그 자리에서 갱신한다.
- 다른 작업인 경우 → **멈추고 묻는다.** 체크되지 않은 태스크는 다른 세션에서 빌드 중일 수 있다. 기존 파일을 임의로 삭제·덮어쓰기·이름 변경하지 않는다. 충돌 상황을 보여 주고 사용자가 결정하게 한다 (기존 계획을 먼저 끝낼지, 명시적으로 버릴지, 새 계획을 어디에 둘지).

같은 규칙이 외부 태스크 목록 위치에도 적용된다. 새 항목을 넣을 자리를 만들려고 다른 계획의 열린 트래커 항목들을 일괄 종료하거나 삭제하지 않는다.

### 태스크 목록 위치

태스크 목록 위치는 태스크와 체크포인트를 기록하는 곳이다. 여기서 한 번만 정의하며, 이 스킬의 다른 모든 언급은 이 정의를 따른다.

- **기본값: `tasks/todo.md`의 체크리스트 형식 마크다운 파일.** `/build` 커맨드를 비롯한 하위 도구들이 전제하는 관례다. 프로젝트가 달리 정하지 않는 한 이것을 쓴다.
- **외부 트래커:** 프로젝트의 에이전트 규칙(`CLAUDE.md`, `AGENTS.md` 등)이나 사용자가 이슈 트래커(예: GitHub Issues, Jira, Linear, `bd`/beads)를 지정하면, `tasks/todo.md`를 쓰는 대신 태스크 하나당 트래커 항목 하나를 만든다. 4단계의 구조를 트래커 필드에 대응시킨다: 인수 기준과 검증 단계는 항목 본문에, 의존 관계는 트래커의 연결 기능(`bd dep add`, "blocked by" 등)으로. 5단계의 체크포인트도 트래커 항목으로 기록하거나, 트래커에 마땅한 대응물이 없으면 계획 문서의 체크리스트로 기록한다.

외부 트래커를 쓸 때는 그 사실을 `tasks/plan.md`에 적어 둬서(예: "태스크는 Linear 프로젝트 FOO에서 추적") 이후 단계와 다음 세션이 어디를 봐야 하는지 알게 한다. 계획 문서의 태스크 목록 절은 중복 체크리스트가 아니라 트래커 항목 id나 링크의 순서 있는 색인으로 유지한다.

## 계획 문서 템플릿

```markdown
# 구현 계획: [기능/프로젝트 이름]

## 개요
[무엇을 만드는지 한 문단 요약]

## 아키텍처 결정
- [핵심 결정 1과 근거]
- [핵심 결정 2와 근거]

## 태스크 목록

### 1단계: 기반
- [ ] 태스크 1: ...
- [ ] 태스크 2: ...

### 체크포인트: 기반
- [ ] 테스트 통과, 빌드 깨끗함

### 2단계: 핵심 기능
- [ ] 태스크 3: ...
- [ ] 태스크 4: ...

### 체크포인트: 핵심 기능
- [ ] 종단 간 플로 동작

### 3단계: 마무리
- [ ] 태스크 5: ...
- [ ] 태스크 6: ...

### 체크포인트: 완료
- [ ] 모든 인수 기준 충족
- [ ] 검토 준비 완료

## 위험과 완화책
| 위험 | 영향 | 완화책 |
|------|--------|------------|
| [위험] | [높음/중간/낮음] | [전략] |

## 미해결 질문
- [사람의 입력이 필요한 질문]
```

태스크가 외부 트래커에 있을 때는 위의 태스크 목록 절을 중복 체크리스트가 아니라 트래커 항목 id나 링크의 순서 있는 색인으로 유지한다.

## 병렬화 기회

여러 에이전트나 세션을 쓸 수 있을 때:

- **병렬화해도 안전:** 서로 독립적인 기능 슬라이스, 이미 구현된 기능에 대한 테스트, 문서
- **반드시 순차적:** 데이터베이스 마이그레이션, 공유 상태 변경, 의존 사슬
- **조율이 필요:** API 계약을 공유하는 기능들 (계약을 먼저 정의하고 그다음 병렬화)

## 흔한 자기합리화

| 자기합리화 | 실제로는 |
|---|---|
| "하면서 알아내면 돼" | 그렇게 해서 엉킨 실타래와 재작업이 나온다. 10분의 계획이 몇 시간을 아낀다. |
| "태스크는 뻔해" | 그래도 적어라. 명시적인 태스크가 숨은 의존 관계와 놓친 엣지 케이스를 드러낸다. |
| "계획은 부대 비용이야" | 계획이 곧 작업이다. 계획 없는 구현은 그냥 타이핑이다. |
| "머릿속에 다 들어 있어" | 컨텍스트 윈도우는 유한하다. 문서로 쓴 계획은 세션 경계와 압축을 넘어 살아남는다. |
| "예전 `tasks/plan.md`는 낡았으니 그냥 갈아엎자" | 체크되지 않은 태스크는 다른 세션에서 빌드 중일 수 있다. 덮어쓰면 그 어디에도 없는 작업 상태가 파괴된다. 멈추고 물어라. |

## 위험 신호

- 문서화된 태스크 목록 없이 구현을 시작한다
- 다른 작업의 체크되지 않은 태스크가 남아 있는 `tasks/plan.md`나 `tasks/todo.md`를 묻지 않고 덮어쓴다
- 프로젝트가 외부 트래커를 지정했는데 `tasks/todo.md`를 쓴다 (또는 태스크를 양쪽에 흩뿌린다)
- 인수 기준 없이 "기능을 구현한다"고만 적힌 태스크
- 계획에 검증 단계가 없다
- 모든 태스크가 XL 크기다
- 태스크 사이에 체크포인트가 없다
- 의존 순서를 고려하지 않았다

## 검증

구현을 시작하기 전에 확인한다:

- [ ] 모든 태스크에 인수 기준이 있다
- [ ] 모든 태스크에 검증 단계가 있다
- [ ] 태스크 의존 관계가 식별되고 올바르게 정렬되었다
- [ ] 태스크가 태스크 목록 위치(기본값 `tasks/todo.md`)에 기록되었다
- [ ] 기존의 미완성 계획을 사용자의 명시적 확인 없이 덮어쓰지 않았다
- [ ] 파일 5개 이상을 건드리는 태스크가 없다
- [ ] 주요 단계 사이에 체크포인트가 있다
- [ ] 사람이 계획을 검토하고 승인했다
