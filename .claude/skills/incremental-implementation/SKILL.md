# 증분 구현 (Incremental Implementation)

## 개요

얇은 수직 슬라이스 단위로 만든다 — 한 조각을 구현하고, 테스트하고, 검증한 다음 확장한다. 기능 전체를 한 번에 구현하지 않는다. 각 증분이 끝나면 시스템은 동작하고 테스트 가능한 상태로 남아야 한다. 이것이 큰 기능을 다룰 만한 것으로 만드는 실행 규율이다.

## 언제 사용하는가

- 여러 파일에 걸친 변경을 구현할 때
- 태스크 분해 결과로부터 새 기능을 만들 때
- 기존 코드를 리팩터링할 때
- 테스트 없이 100줄 넘게 쓰고 싶어질 때마다

**사용하지 않을 때:** 이미 범위가 최소인 단일 파일·단일 함수 변경.

## 증분 사이클

```
┌──────────────────────────────────────┐
│                                      │
│    구현  ──→  테스트  ──→  검증  ──┐   │
│      ▲                           │   │
│      └────── 커밋  ◄─────────────┘   │
│              │                       │
│              ▼                       │
│          다음 슬라이스                  │
│                                      │
└──────────────────────────────────────┘
```

각 슬라이스마다:

1. **구현** — 가장 작은 완결된 기능 조각을 구현한다
2. **테스트** — 테스트 스위트를 돌린다 (없으면 테스트를 쓴다)
3. **검증** — 슬라이스가 기대대로 동작하는지 확인한다 (테스트 통과, 빌드 성공, 수동 확인)
4. **커밋** — 설명이 담긴 메시지로 진척을 저장한다. 커밋 하나가 논리적으로 한 가지만 바꾼다
5. **다음 슬라이스로** — 이어 나가되, 처음부터 다시 시작하지 않는다

## 슬라이싱 전략

### 수직 슬라이스 (권장)

스택을 관통하는 하나의 완결된 경로를 만든다:

```
슬라이스 1: 할 일 생성 (엔티티 + 리포지토리 + 서비스 + POST 엔드포인트)
    → 테스트 통과, POST /api/tasks 가 201을 반환함

슬라이스 2: 할 일 목록 (조회 + 페이징 + GET 엔드포인트)
    → 테스트 통과, GET /api/tasks 가 페이지를 반환함

슬라이스 3: 할 일 수정 (상태 전이 + PATCH 엔드포인트)
    → 테스트 통과, 도메인 규칙을 어기는 전이가 거부됨

슬라이스 4: 할 일 삭제 (삭제 + 권한 확인 + DELETE 엔드포인트)
    → 테스트 통과, CRUD 전체 완성
```

각 슬라이스는 종단 간으로 동작하는 기능을 전달한다.

### 계약 우선 슬라이싱

여러 계층이나 여러 사람이 병렬로 개발되어야 할 때:

```
슬라이스 0: API 계약 정의 (요청/응답 record, OpenAPI 명세)
슬라이스 1a: 계약에 맞춰 도메인·서비스 구현 + 단위 테스트
슬라이스 1b: 계약대로 응답하는 컨트롤러 + @WebMvcTest (서비스는 목)
슬라이스 2: 통합하고 @SpringBootTest로 종단 간 테스트
```

### 위험 우선 슬라이싱

가장 위험하거나 가장 불확실한 조각을 먼저 친다:

```
슬라이스 1: WebSocket 연결이 동작함을 증명 (최고 위험)
슬라이스 2: 검증된 연결 위에 실시간 할 일 갱신 구축
슬라이스 3: 오프라인 지원과 재연결 추가
```

슬라이스 1이 실패하면, 슬라이스 2와 3에 투자하기 전에 그 사실을 알게 된다.

## 구현 규칙

### 규칙 0: 단순함이 먼저

코드를 쓰기 전에 묻는다: "동작할 수 있는 가장 단순한 것은 무엇인가?"

코드를 쓴 뒤에는 다음 항목으로 되짚는다:
- 이걸 더 적은 줄로 할 수 있는가?
- 이 추상화들이 자기 복잡도만큼 값을 하는가?
- 스태프 엔지니어가 이걸 보고 "그냥 ...하면 되잖아"라고 말하지 않을까?
- 지금의 태스크가 아니라 가상의 미래 요구사항을 위해 만들고 있지는 않은가?

```
단순함 점검:
✗ 알림 하나 때문에 만든 범용 이벤트 디스패처와 핸들러 등록 체계
✓ 서비스에서 직접 호출하는 메서드 하나

✗ 구현체가 둘뿐인데 도입한 추상 팩토리와 전략 패턴
✓ 공용 로직을 공유하는 직관적인 클래스 두 개

✗ 검증 규칙 세 개를 위한 설정 기반 규칙 엔진
✓ 검증 메서드 세 개
```

비슷한 코드 세 줄이 성급한 추상화보다 낫다. 순진하고 명백히 옳은 버전을 먼저 구현한다. 최적화는 테스트로 정확성이 입증된 뒤에만 한다.

### 규칙 0.5: 범위 규율

태스크가 요구하는 것만 건드린다.

하지 않는다:
- 변경 지점 옆의 코드를 "정리"하기
- 수정하지 않는 파일의 import를 리팩터링하기
- 완전히 이해하지 못한 주석을 지우기
- "유용해 보인다"는 이유로 명세에 없는 기능을 추가하기
- 읽기만 하는 파일의 문법을 최신화하기

태스크 범위 밖에서 개선할 만한 것을 발견하면, 고치지 말고 기록만 한다:

```
발견했지만 건드리지 않음:
- DateFormatter에 쓰이지 않는 import가 있음 (이번 태스크와 무관)
- SecurityConfig의 인증 실패 메시지를 개선할 수 있음 (별도 태스크)
→ 이것들로 태스크를 만들까요?
```

### 규칙 1: 한 번에 하나씩

각 증분은 논리적으로 하나만 바꾼다. 관심사를 섞지 않는다:

**나쁨:** 새 컴포넌트를 추가하고, 기존 컴포넌트를 리팩터링하고, 빌드 설정을 갱신하는 커밋 하나.

**좋음:** 변경마다 하나씩, 별도의 커밋 세 개.

### 규칙 2: 항상 빌드되게 유지한다

각 증분이 끝난 뒤 프로젝트는 빌드되어야 하고 기존 테스트는 통과해야 한다. 슬라이스 사이에 코드베이스를 깨진 상태로 두지 않는다.

### 규칙 3: 미완성 기능에는 피처 플래그

기능이 아직 사용자에게 내보낼 준비가 안 됐는데 증분을 머지해야 한다면:

```java
// application.yml: feature.task-sharing.enabled: false

@Service
@ConditionalOnProperty(name = "feature.task-sharing.enabled", havingValue = "true")
public class TaskSharingService {
    // 작업 중인 공유 기능. 플래그가 꺼져 있으면 빈으로 등록조차 되지 않는다
}
```

이렇게 하면 미완성 작업을 노출하지 않고도 작은 증분을 메인 브랜치에 머지할 수 있다.

### 규칙 4: 안전한 기본값

새 코드는 안전하고 보수적인 동작을 기본값으로 한다:

```java
// 안전: 기본은 꺼짐, 켜려면 명시해야 한다
// Java에는 기본값 인자가 없으므로 오버로드로 기본값을 표현한다
public TaskResponse create(CreateTaskRequest request) {
    return create(request, NotificationPolicy.SILENT);
}

public TaskResponse create(CreateTaskRequest request, NotificationPolicy policy) {
    // ...
}
```

### 규칙 5: 되돌리기 쉽게

각 증분은 독립적으로 되돌릴 수 있어야 한다:

- 추가형 변경(새 파일, 새 함수)은 되돌리기 쉽다
- 기존 코드 수정은 최소한으로, 초점을 좁혀서 한다
- 데이터베이스 마이그레이션에는 대응하는 롤백 마이그레이션이 있어야 한다
- 한 커밋에서 무언가를 지우고 같은 커밋에서 교체하지 않는다 — 분리한다

## 에이전트와 함께 일하기

에이전트에게 증분 구현을 지시할 때:

```
"계획의 태스크 3을 구현하자.

엔티티와 리포지토리만 먼저 한다.
컨트롤러는 아직 건드리지 마라 — 다음 증분에서 한다.

구현한 뒤에는 ./gradlew test 와 ./gradlew build 를 돌려서
깨진 게 없는지 검증해라."
```

각 증분에서 무엇이 범위 안이고 무엇이 범위 밖인지 명시한다.

## 증분 체크리스트

각 증분 후, 저장소 자체의 명령으로 검증한다:

- [ ] 변경이 한 가지 일을 하고, 그것을 완전히 한다
- [ ] 기존 테스트가 모두 여전히 통과한다 (`./gradlew test`)
- [ ] 빌드가 성공한다 (`./gradlew build`)
- [ ] 컴파일이 통과한다 (`./gradlew compileJava`)
- [ ] 새 기능이 기대대로 동작한다
- [ ] 변경이 설명이 담긴 메시지로 커밋되었다

**참고:** 각 검증 명령은 그 결과에 영향을 줄 수 있는 변경 이후에 돌린다. 한 번 성공한 뒤에는 코드가 바뀌지 않았다면 같은 명령을 반복하지 않는다 — 바뀌지 않은 코드에 다시 돌려 봐야 새로운 정보가 없다.

## 흔한 자기합리화

| 자기합리화 | 실제로는 |
|---|---|
| "마지막에 한꺼번에 테스트할게" | 버그는 복리로 쌓인다. 슬라이스 1의 버그가 슬라이스 2~5를 전부 틀리게 만든다. 슬라이스마다 테스트한다. |
| "한 번에 하는 게 더 빨라" | 뭔가 깨지고 바뀐 500줄 중 어느 줄 때문인지 못 찾기 전까지만 빠르게 *느껴진다*. |
| "이 변경들은 너무 작아서 따로 커밋할 게 없어" | 작은 커밋은 공짜다. 큰 커밋은 버그를 숨기고 롤백을 고통스럽게 만든다. |
| "피처 플래그는 나중에 넣을게" | 기능이 완성되지 않았다면 사용자에게 보이면 안 된다. 플래그는 지금 넣는다. |
| "이 리팩터는 작으니까 같이 넣자" | 기능과 섞인 리팩터는 양쪽 모두를 검토하고 디버깅하기 어렵게 만든다. 분리한다. |
| "혹시 모르니 빌드 명령을 한 번 더 돌려 보자" | 한 번 성공한 뒤 같은 명령을 반복해 봐야, 그사이 코드가 바뀌지 않았다면 얻는 게 없다. 안심하려고가 아니라 이후 수정 뒤에 다시 돌린다. |

## 위험 신호

- 테스트를 돌리지 않고 100줄 넘게 코드를 썼다
- 하나의 증분에 서로 무관한 변경이 여러 개 들어 있다
- "이것도 빨리 같이 넣자" 식의 범위 확장
- 더 빨리 가려고 테스트·검증 단계를 건너뛴다
- 증분 사이에 빌드나 테스트가 깨져 있다
- 커밋되지 않은 큰 변경이 쌓인다
- 세 번째 사용처가 요구하기도 전에 추상화를 만든다
- "온 김에" 태스크 범위 밖의 파일을 건드린다
- 일회성 작업을 위해 새 유틸리티 파일을 만든다
- 코드 변경이 전혀 없는데 같은 빌드·테스트 명령을 연달아 두 번 돌린다

## 검증

한 태스크의 모든 증분을 마친 뒤:

- [ ] 각 증분이 개별적으로 테스트되고 커밋되었다
- [ ] 전체 테스트 스위트가 통과한다
- [ ] 빌드가 깨끗하다
- [ ] 기능이 명세대로 종단 간 동작한다
- [ ] 커밋되지 않은 변경이 남아 있지 않다

## 함께 보기

증분별 검증은 국소적인 확인이다. 태스크를 완료로 선언하기 전에, 태스크와 무관하게 모든 증분이 넘어야 하는 상시 기준선인 프로젝트 전체의 완료 정의(Definition of Done)를 최종 관문으로 적용한다. `../../references/definition-of-done.md`를 참고한다.
