# 완료 정의 (Definition of Done)

모든 변경이 완료로 인정되기 전에 넘어야 하는 **프로젝트 상시 기준선**이다. 태스크마다 달라지며 "우리가 옳은 것을 만들었는가?"에 답하는 인수 기준과 달리, 완료 정의는 언제나 같고 "우리 기준으로 끝난 것인가?"에 답한다. `planning-and-task-breakdown`과 `incremental-implementation`에서 최종 관문으로 쓴다.

## 완료 정의 vs 인수 기준

| | 인수 기준 | 완료 정의 |
|---|---|---|
| 범위 | 하나의 태스크나 명세에 한정 | 모든 증분에 적용 |
| 변화 | 항목마다 다름 | 고정되어 재사용 |
| 답하는 질문 | "*이것*을 만들었는가?" | "*내보낼 수 있는가?*" |
| 정하는 시점 | 태스크를 계획할 때 | 프로젝트에서 한 번 |
| 예시 | "이메일 링크로 비밀번호를 재설정할 수 있다" | "테스트 통과, 회귀 없음, 문서 갱신" |

둘은 상호 보완적이다. 태스크는 **그 태스크의** 인수 기준을 만족하고 **동시에** 상시 완료 정의를 만족할 때에만 완료다. 어느 한쪽을 건너뛰면 끝난 것처럼 보이지만 끝나지 않은 작업이 남는다.

## 상시 체크리스트

모든 변경에 대해 완료를 선언하기 전에 적용한다.

### 정확성

- [ ] 태스크의 인수 기준을 모두 만족한다
- [ ] 컴파일이나 타입 검사만이 아니라 **실제로 실행해** 의도대로 동작함을 확인했다
- [ ] 새 동작이 인수 기준을 실제로 검증하는 테스트로 덮여 있다 — 무엇을 망가뜨려도 통과하는 테스트는 덮은 것이 아니다
- [ ] 기존 테스트가 여전히 통과한다 (`./gradlew test`). 회귀를 만들지 않았다
- [ ] 행복 경로만이 아니라 엣지 케이스와 에러 경로를 처리했다

### 품질

- [ ] 이름과 구조로 의도가 드러난다. *무엇을* 하는지 설명하는 주석이 필요 없다
- [ ] 비즈니스 로직이 중복되지 않는다
- [ ] 죽은 코드, 디버그 출력, 주석 처리된 블록을 남기지 않았다
- [ ] 변경이 태스크 범위 안에 있다. 무관한 리팩터가 섞여 들어가지 않았다
- [ ] `./gradlew build`가 통과하고 새로운 컴파일 경고를 만들지 않았다

### 통합

- [ ] 격리된 상태만이 아니라 시스템의 나머지와 함께 동작한다
- [ ] 데이터베이스 마이그레이션, 설정 변경, 피처 플래그를 반영했다
- [ ] 공개 인터페이스나 API를 바꿨다면 하위 호환성을 검토했다

### 문서화

- [ ] 공개 인터페이스, API, 사용자에게 보이는 동작을 문서화했다
- [ ] 보존할 가치가 있는 아키텍처 결정을 기록했다
- [ ] 문서가 변경 이력이 아니라 **현재 상태**를 시제 없는 문장으로 서술한다

### 내보낼 준비

- [ ] 신뢰할 수 없는 입력, 인증, 데이터 처리에 대한 보안 영향을 검토했다
- [ ] 새로 생긴 중요 경로에 로그·메트릭이 있다
- [ ] 위험한 변경에는 되돌릴 경로가 있다
- [ ] 머지나 배포 전에 사람이 검토하고 승인했다

## 적용 방법

- **태스크 단위**: 태스크를 체크하기 전에 정확성과 품질 절을 확인한다.
- **기능 단위**: 기능을 완료로 보기 전에 통합과 문서화 절을 확인한다.
- **릴리스 단위**: 전체 체크리스트가 최저선이다.

프로젝트에 맞게 한 번 다듬은 뒤에는 그대로 재사용한다. 매번 다시 협상하는 완료 정의는 완료 정의가 아니다.

## 위험 신호

- "다 됐어요, 아직 실행만 안 해 봤어요" — 검증되지 않은 작업은 완료가 아니다.
- 문서, 회귀, 실행 확인을 건너뛴 채 "테스트 통과"를 완료와 같은 말로 쓴다.
- 마감 압박에 따라 다른 기준을 적용한다.
- 인수 기준을 기준의 전부로 취급하고, 상시 품질 최저선이 없다.
- 사람의 검토가 필요한 변경인데 검토 전에 완료를 선언한다.
