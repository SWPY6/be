# 명세: 종목 마스터 적재 (stock-master)

`stocks`·`markets`를 KIS 종목정보 파일로 채운다. 지금 72종목(전부 손으로 넣은 테스트
데이터)을 **8,227종목**으로 바꾼다.

주요 변동 종목 목록의 `stockId`가 거의 언제나 `null`인 것이 이 작업의 동기다. 운영에서
`condition=RISING` 54건이 **전부** `null`이었고, 그래서 사용자가 종목 상세로 넘어갈 수 없다.

## 내가 세운 전제

1. **종목 상세 화면의 값은 이 범위가 아니다.** 대표자명·유동주식수·로고는 어느 출처도 주지
   않는다. `null`로 두고, 필요해지면 별도로 채운다.
2. **산업 매핑은 이 범위가 아니다.** 업종코드를 우리 9개 산업으로 옮기는 매핑표는 분량이
   달라 따로 다룬다(「다음 단계」에 조사 결과를 남겼다).
3. **S&P 500 구성 목록은 이 범위가 아니다.** 종목정보 파일에 지수 소속이 없다(실측).
4. **적재는 사람이 실행한다.** 운영이 `ddl-auto=none`이고 `db/seed-industries.sql`·
   `db/seed-test-stocks.sql`이 이미 그 방식이다. 배치로 만들지 않는다.

## 규칙

### 출처 — KIS 종목정보 파일

```
https://new.real.download.dws.co.kr/common/master/kospi_code.mst.zip
https://new.real.download.dws.co.kr/common/master/kosdaq_code.mst.zip
https://new.real.download.dws.co.kr/common/master/nasmst.cod.zip
https://new.real.download.dws.co.kr/common/master/nysmst.cod.zip
```

`dws.co.kr`은 한국투자증권 도메인이다. **인증이 없다** — APP_KEY 를 쓰지 않는다.
매일 갱신된다(`Last-Modified` 확인).

**KIS REST API 에는 전 종목 목록 엔드포인트가 없다.** 종목코드를 이미 알고 하나씩 묻는
구조이고, 순위 API 는 상위 30·100건만 준다. 종목 **목록**을 얻는 경로는 이 파일뿐이다.

⚠️ **이 URL 은 API 계약이 아니라 관행이다.** 개발자센터 문서의 엔드포인트가 아니라 KIS 가
공개한 예제 코드(`koreainvestment/open-trading-api`)가 쓰는 정적 경로다. 경로가 바뀌어도
공지가 없다. **그래서 운영 코드가 이 URL 을 긁지 않는다** — 사람이 받아 SQL 로 남긴다.
깨져도 운영이 멈추지 않는다.

### 시장은 네 개다 — 파일이 곧 시장

```
kospi_code.mst  → KOSPI    (KR, KRW)   exchange = KRX
kosdaq_code.mst → KOSDAQ   (KR, KRW)   exchange = KRX
NASMST.COD      → NASDAQ   (US, USD)   exchange = NASDAQ
NYSMST.COD      → NYSE     (US, USD)   exchange = NYSE
```

**`SP500` 시장을 쓰지 않는다.** S&P 500 은 지수이고, 구성 종목이 나스닥과 뉴욕에 걸쳐
있다. 지수를 시장으로 쓰면 뉴욕 비구성 종목 2,000여 개를 담을 자리가 없고, 애플처럼
`NASDAQ`과 `SP500` 둘에 속하는 종목이 생긴다. 그러면 `matchByTicker`가 "한 코드에 둘 이상
걸리면 버린다"는 규칙으로 **그 종목을 버린다** — 사용자가 가장 많이 찾는 500개가
`stockId: null`이 된다.

지금 해외 36종목이 `SP500`에 있다. **실제 거래소로 옮긴다**(`UPDATE`). 36개는 전부 S&P 500
구성 종목이라 라벨이 참이었지만, 6,409개에서는 대부분 거짓이 된다 — 전제가 범위를 벗어난다.

**티커가 시장을 가로질러 겹치지 않는다**(실측). 나스닥·뉴욕 겹침 0, 코스피·코스닥 겹침 0.
그래서 모든 티커가 정확히 한 시장에 속하고 `matchByTicker`가 아무도 버리지 않는다.

**`status`를 `ACTIVE`로 고정한다.** 국내 파일에 거래정지·관리종목 플래그가 있지만 **매일
바뀌는 값**이고, `StockStatus`를 판단에 쓰는 코드가 0건이다. 하루 지나면 틀릴 값을
8,227행에 박아 넣지 않는다.

**`float_shares`에 상장주수를 넣지 않는다.** 이름이 다른 개념이다.

```
상장주수     상장된 전체 주식          (파일이 주는 값, 천주 단위)
float_shares 대주주·자기주식을 뺀 유통분 (필드가 뜻하는 값)
```

읽는 코드가 0건이므로 `null`이 정직하다. 넣으면 필드 이름이 거짓이 되고, 나중에
유동주식수로 계산하는 사람이 틀린 값을 쓴다.

**`ticker`가 6자리 숫자라고 가정하지 않는다.** 신형우선주는 `00088K`(한화3우B)처럼 영문이
섞이고, 해외 우선주는 `JPM/C`처럼 슬래시가 들어간다. 국내에만 85건 있다.

## 선행 조건 — 내가 함께 구현한다

### ① `MarketCode`에 `NYSE`를 더한다

```java
public enum MarketCode { KOSPI, KOSDAQ, NASDAQ, NYSE, SP500 }
```

`SP500`은 **지우지 않는다** — 쓰지 않을 뿐이다. 지우면 기존 36종목의 `market_id`를 옮기기
전에 읽기가 깨진다.

`markets.code`는 `@Enumerated(STRING)`이고 `industries.name`과 매핑이 같다. 그쪽이 네이티브
`ENUM` 컬럼이므로 **`ALTER TABLE markets MODIFY code enum(...)`이 먼저 필요하다.**
적재 전에 서버에서 확인한다.

```bash
SHOW CREATE TABLE markets\G
```

### ② `ceo`·`listed_at`·`float_shares`를 nullable 로 바꾼다

**넓히기라 배포 전에 해도 안전하다.** 읽는 코드를 전부 찾았다.

| 필드 | 읽는 코드 | |
| --- | --- | --- |
| `ceo` | 0건 | 그대로 안전 |
| `float_shares` | 0건 | 그대로 안전 |
| `listed_at` | **1건** | ⚠️ 가드가 필요하다 |

```java
// StockDailyPriceSyncPolicy:38
boolean startCovered = stored.startsOnOrBefore(from) || stock.listedAfter(from);
```

`listedAfter`가 `listedAt.isAfter(date)`라서 **`null`이면 NPE** 다. 해외 종목 차트를 열면
바로 터진다. **이것만은 버그 취급**이라 재현 테스트를 먼저 쓰고 실패를 확인한 뒤 고친다.

```java
public boolean listedAfter(LocalDate date) {
    return listedAt != null && listedAt.isAfter(date);
}
```

상장일을 모르면 "그 날짜 이후 상장"이라 단정할 수 없으니 `false`다. 호출처에서 `false`면
일봉을 **한 번 더 받으러 가는** 쪽으로 흐르니 안전한 방향이다.

## 프로젝트 구조

운영 코드를 추가하지 않는다. `db/` 아래 SQL 과 엔티티·enum 수정뿐이다.

```
db/ddl-stocks-nullable.sql       ceo·listed_at·float_shares → NULL
db/ddl-markets-code-nyse.sql     markets.code enum 에 NYSE
db/seed-markets.sql              KOSDAQ·NASDAQ·NYSE 3행 + 기존 36종목 market_id 이전
db/seed-stocks-kospi.sql         914
db/seed-stocks-kosdaq.sql        1,805
db/seed-stocks-nasdaq.sql        3,8xx
db/seed-stocks-nyse.sql          2,2xx
```

시장별로 나눈다 — 한 파일이 너무 커지면 실행 중 끊겼을 때 어디까지 들어갔는지 알기 어렵다.
전부 `INSERT ... ON DUPLICATE KEY UPDATE`로 써서 **여러 번 실행해도 결과가 같게** 한다
(`seed-industries.sql`과 같은 방식).

**`stock_id`를 명시하지 않는다.** `auto_increment`에 맡긴다 — 기존 테스트 데이터가
9001~9072를 쓰고 있어 범위가 겹치지 않는다.

## 테스트 전략

적재 자체는 SQL 이라 테스트 대상이 아니다. 테스트는 **코드 변경**에만 붙인다.

| 대상 | 종류 | 무엇을 |
| --- | --- | --- |
| `Stocks.listedAfter` | 단위 | `listedAt`이 `null`이면 `false` (재현 테스트 먼저) |
| `StockDailyPriceSyncPolicy` | 단위 | 상장일을 모르는 종목이 NPE 없이 흐른다 |
| `JpaStockReaderTest` | 슬라이스 | `ceo`·`listed_at`이 `null`인 종목을 읽는다 |

파싱 결과는 테스트가 아니라 **적재 전 검사**로 지킨다 — 상장일 전수 검사, 건수 대조,
삼성전자·애플 샘플 대조.

## 경계

- **배치를 만들지 않는다.** 마스터 파일을 주기적으로 긁지 않는다.
- **조회 경로가 쓰기를 하지 않는다.** 순위에 있고 DB 에 없는 종목을 insert 하지 않는다 —
  모집단이 수요에 끌려가면 "전체 종목" 탭이 전체가 아니게 된다(일봉에서 겪은 함정).
- **상장폐지를 처리하지 않는다.** 파일에서 사라진 종목을 `DELISTED`로 바꾸지 않는다.
- **종목 상세의 값을 채우지 않는다.** 대표자명·유동주식수·로고.

1. `stocks`에 8,2xx행이 있다
2. `markets`에 `KOSPI`·`KOSDAQ`·`NASDAQ`·`NYSE` 네 행이 있고 `SP500`에 속한 종목이 0이다

## 미해결 질문

1. **SQL 파일 크기를 저장소에 둘지.** 8,227행이면 합계 2MB 가까이 된다. `db/`의 기존
   파일은 19KB 가 최대다. 큰 파일을 커밋하지 않으려면 생성 스크립트만 두고 SQL 은
   저장소 밖에 둬야 하는데, 그러면 "실행한 DDL 을 기록으로 남긴다"는 방식과 어긋난다.
2. **종목 담당과 겹치는지.** `uk_stocks_ticker_market` 유일 제약 때문에 양쪽이 같은 종목을
   넣으면 한쪽이 막힌다. `seed-test-stocks.sql`이 "종목 담당의 실제 데이터가 들어오기
   전까지"라고 적어 뒀다.
3. **기존 테스트 데이터 72행을 지울지.** 실제 데이터와 중복되는 종목이 있다.

## 알려진 한계

### 해외 상장일이 없다

`stock_daily_prices` 동기화가 "상장 전이라 봉이 없는 것"과 "덜 받은 것"을 구분하지 못해,
해외 종목 차트를 열 때마다 일봉을 한 번 더 받으러 간다. KIS 주식기본조회(`CTPF1002R`)를
종목당 부르면 채울 수 있지만 6,409 호출이고, 클라이언트에 호출 제한 장치가 없다.

### 파일이 하루 지난 값일 수 있다

`Last-Modified`가 매일 갱신되지만 우리가 받는 시점은 사람이 정한다. 신규 상장 종목은
다음 적재까지 `stockId: null`이다. 문제가 되면 **순위에 있고 DB 에 없는 티커를 `WARN`으로
남기는 것**부터 시작한다 — 종목 마스터를 오염시키지 않고 "다시 받을 때가 됐다"는 신호만 준다.

### 상장폐지가 남는다

파일에서 사라진 종목이 `ACTIVE`로 남는다. `status`를 판단에 쓰는 코드가 0건이라 지금은
영향이 없지만, 쓰기 시작하면 정리 규칙이 필요하다.
